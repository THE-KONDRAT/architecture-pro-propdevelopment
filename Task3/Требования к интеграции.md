# Требования к внешним интеграциям

Под внешними интеграциями понимается:
- Интеграция контейнеров home-access-service, vehicle-service, biometric-service
PropDevelopment с API платформы партнёра «Умный дом» (домофоны, шлагбаумы).
- Интеграция контейнеров tenant-core-app PropDevelopment с API поставщиков ресурсов ЖКХ и с платёжной системой.

# Общее
Требуется использовать HTTPS с TLS не ниже 1.2.
Все события интеграции должны записываться в журнал и передаваться в SIEM.
Взаимодействие должно ограничивается только по исходящим соединениям от PropDevelopment (на текущий момент), исключение – платёжная система, там разрешены запросы по mTLS.

## Требования к безопасности и данным
1. Партнёру передаются только технические идентификаторы и минимальная необходимая информация (ID дома, ID домофона/шлагбаума, номер квартиры/парковочного места). ФИО, телефоны, договоры собственников не передаются.
2. При необходимости передачи конфиденциальной информации, идентифицирующей клиента, необходимо убедиться, что контрагент соблюдает законы о защите персональных данных.
3. Биометрические данные (шаблоны лиц, изображения, номера ТС) обрабатываются только внутри PropDevelopment (biometric-service, vehicle-service).
Хранение осуществляется в зашифрованном виде с ключами из KMS.
4. Команды открытия передаются с идентификатором инициатора (ID пользователя мобильного приложения), персональные данные при этом не передаются.
5. Платформа партнёра не должна запрашивать данные, не обусловленные ТЗ услуг, при попытке такого запроса необходимо срабатывание алерта в SIEM.

## Аутентификация и авторизация
### Сервисы PropDevelopment к платформе «Умный дом»
- Аутентификация: OAuth 2.0, flow (grant type) `client_credentials` (client_id + client_secret, хранятся в защищённом хранилище секретов).
- Access Token в формате JWT со сроком жизни до 15 минут с минимально необходимыми правами.

### Сервисы PropDevelopment к поставщикам ресурсов ЖКХ
- Аутентификация – API Key. 
- Ротация ключа осуществляется за период до 180 дней, при компрометации API Key процедура отзыва и ротации должна занимать менее 3 часов.
- Хранение ключа осуществляется в защищённом хранилище секретов

### Сервисы PropDevelopment к платёжной системе
- Аутентификация: OAuth 2.0, flow (grant type) `client_credentials` (client_id + client_secret, хранятся в защищённом хранилище секретов).
- Access Token в формате JWT со сроком жизни до 5 минут с минимально необходимыми правами.
- Взаимная TLS-аутентификация (mTLS)
- Уведомления о статусе платежа осуществляются через webhook с подписью HMAC-SHA256.
- При компрометации секрета процедура отзыва и ротации должна занимать менее 1 часа.

## Организация взаимодействия
### Платформа «Умный дом»
REST API, JSON.
Доставка событий платформы (звонок домофона, распознанный номер, статус устройства): исходящий опрос (polling) с периодичностью ≤ 2 с для событий звонка.
При возникновении проблем с производительностью, можно рассмотреть переход на систему подписки на события.
Команды открытия: синхронный вызов с таймаутом ≤ 5 с.
Идемпотентность обеспечивается путём передачи уникального идентификатора.
При сетевых ошибках или 5xx предпринимаются повторные попытки вызова с экспоненциально увеличивающимся периодом.
API партнёра должно поддерживать минимум две версии при обновлении API.
Целевой SLA ≥ 99,5%. При недоступности платформы функции «Умный дом» деградируют без влияния на остальные сервисы.

### Поставщик ресурсов ЖКХ
Протокол использовать существующий, ограничить только передаваемые данные.
В случае запроса персональных данных, вместо них возвращаются заглушки, а факт такого запроса фиксируется в SIEM.
Таймаут вызова – до 10с.
При сетевых ошибках или 5xx предпринимаются повторные попытки вызова с экспоненциально увеличивающимся периодом.

### Платёжная система
REST API, JSON.
Таймаут вызова – до 10с.
Идемпотентность обеспечивается путём передачи уникального идентификатора.
Должна обеспечиваться идемпотентность обработки статусов от платёжной системы и учитываться timestamp уведомления.
При совершении оплаты необходима сверка суммы с внутренним заказом, а при их расхождении выдача ошибки и запись инцидента в журнал и отправка в SIEM.
При сетевых ошибках или 5xx предпринимаются повторные попытки вызова с экспоненциально увеличивающимся периодом.
API партнёра должно поддерживать минимум две версии при обновлении API.
Целевой SLA ≥ 99,5%. При недоступности платформы функции осуществления платежей деградируют без влияния на остальные сервисы.
