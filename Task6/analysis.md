# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. Доступ к секретам:
    - Кто: minikube-user, группа system:masters (действовал от имени system:serviceaccount:secure-ops:monitoring)
    - Где: create selfsubjectaccessreviews и list secrets в namespace kube-system
    - Почему подозрительно: сервисный аккаунт из namespace secure-ops проверяет права, затем пытается прочитать секреты. Возможна атака с целью повышения привилегий. Оба запроса отклонены с кодом 403, попытки зафиксированы. 

2. Привилегированные поды:
    - Кто: minikube-user
    - Комментарий: создан под privileged-pod в namespace secure-ops с securityContext.privileged: true, то есть контейнер может получить root-доступ к хосту. Под создан без проблем (код 201).

3. Использование kubectl exec в чужом поде:
    - Кто: minikube-user
    - Что делал: запросы к субресурсу pods/exec пода CoreDNS в namespace kube-system. Исполнение команды упало (в distroless-образе coredns нет cat), но запрос зафиксирован и предотвращён.

4. Создание RoleBinding с правами cluster-admin:
    - Кто: minikube-user
    - К чему привело: создан RoleBinding escalate-binding в namespace secure-ops, повышающий привилегии какого-то из сервисных аккаунтов, привязывая его к роли cluster-admin. Любой, завладевший токеном этого аккаунта, получает полный контроль над кластером.

5. Удаление audit-policy.yaml:
    - Кто: minikube-user от имени admin
    - Возможные последствия: попытка отключить политику аудита (предотвращено, ответ 403), удаление политики лишило бы кластер аудита всех последующих действий атакующего.

## Вывод

Пользователь minikube-user входит в system:masters и действует без ограничений, не соблюдается принцип минимальных привилегий.
Доступна имперсонация без ограничений.
Есть возможность эскалации прав через создание биндингов на cluster-admin, а изменения RBAC логируются без тела запроса: по audit.log нельзя установить, к какой роли привязан escalate-binding. Политика аудита должна покрывать группу rbac.authorization.k8s.io на уровне RequestResponse.
Создание привилегированных подов ничем не ограничено.
Попытка удаления политики аудита блокируется только RBAC; отдельной защиты конфигурации аудита нет.
Тем не менее были отклонены попытки чтения секретов и удаления политики
